# CLAUDE.md — Le Club by LCS

## Projet

**Le Club by LCS** : application d'abonnement mensuel pour triathlètes, coachés par **Martin**.

- Abonnement : **49 € / mois, sans engagement**.
- Lancement : **1er janvier 2027**.

## Stack

- **Next.js** + **TypeScript**
- **Supabase** : authentification, base de données, temps réel, stockage
- **Stripe** : paiements et abonnements
- **Resend** : e-mails
- **Vercel** : déploiement
- Application web **installable sur téléphone** (PWA)

## Langue et formats

- Interface entièrement en **français**.
- Dates et heures au **format français** (ex. `18/11/2026`, `14 h 30`), fuseau **Europe/Paris**.

## Design

La maquette est dans le dossier `maquette/`. Respecter le style **Neon Glassmorphism** de `maquette/Main-neon.dc.html` :

- Mode sombre sur fond **#090A0F**.
- Cartes en **verre fumé translucide avec flou** (backdrop blur).
- **Bordure dégradée de 1 px**.
- **Lueur interne** sur les cartes.
- **Ombre colorée** sous les boutons principaux.
- **Barre d'onglets flottante**.

## Règles métier

- **Pas d'appel direct entre athlète et coach** : uniquement les canaux collectifs et la boîte à questions (**sans votes**).
- Le coach voit l'historique d'un athlète **en lecture seule**.
- Le **RPE** et les **commentaires** de séance sont lus seulement par le membre et l'encadrement (coachs et admins) : sécurité au niveau des lignes dans Supabase, jamais exposés à d'autres membres. Pas de case « douleur » : on ne collecte pas de données de santé.
- Le programme **n'est jamais téléchargeable en PDF** : il reste dans l'app.
- Les ressources se **débloquent selon l'ancienneté** du membre.
- L'athlète **choisit lui-même** :
  - son **niveau** : Finisher, Challenger, Performer ;
  - son **profil** : extensif, intensif.

## Méthode de travail

1. **Avant chaque étape** : proposer un plan court et **attendre l'accord** avant de coder.
2. **Après chaque étape** :
   - lancer les tests ;
   - expliquer **en une phrase simple** ce qui marche ;
   - faire un **commit**.

## Commandes

- `npm run dev` : lancer l'app en local
- `npm test` : tests (Vitest ; les tests de sécurité RLS utilisent une base PostgreSQL locale via `TEST_DATABASE_URL`)
- `npm run typecheck` / `npm run lint` / `npm run build`
- `npm run test:e2e` (après `npm run build`) : vérifie dans un navigateur que chaque écran tient dans la largeur, sans déborder : téléphone (320, 360, 390 px : `affichage-telephone.test.ts`), iPad (768 × 1024, 1024 × 768, tactile : `affichage-tablette.test.ts`) et ordinateur (fenêtre de 1024 px à la souris, 1280, 1440, 1920 px : `affichage-ordinateur.test.ts`), fichiers lancés en parallèle ; navigation de chaque écran membre à 1024, 1280 et 1440 px (`navigation.test.ts` : barre du bas à 1024 px, menu latéral à partir de 1100 px, ni l'un ni l'autre sur les écrans plein écran, bon onglet en cours ; attendu tiré de `src/lib/onglets.ts`). Liste des écrans dans `tests-e2e/ecrans.ts` (**tout nouvel écran doit y être ajouté** ; `tests/apercus-testes.test.ts` échoue si un aperçu y manque). Les écrans connectés sont testés via les pages d'aperçu `/apercu-espace/…` et `/apercu-membre/…` (données fictives, actives seulement avec `APERCU=1`, jamais en production).
- `npm run comparer-affichage` (après `npm run build` ; `-- --ref <branche>` pour une autre référence que `origin/main`, `-- --ecrans <morceau d'adresse>` pour filtrer) : photographie chaque écran sur téléphone et iPad, sur la branche et sur la référence (copie compilée dans `.captures/reference`, une fois par commit), et compare pixel par pixel ; écarts en images dans `.captures/differences`. À lancer à chaque étape de la version ordinateur : il doit répondre « Aucun changement sur téléphone ni sur iPad ».

- `npm run test:paiement` : parcours de paiement de bout en bout avec les faux paiements Stripe (mode test → webhook en ligne → Supabase en ligne) ; hors vérifications GitHub ; nettoie tout à la fin. Variables : `STRIPE_SECRET_KEY` (sk_test_…), `SUPABASE_PROJECT_REF`, `SUPABASE_ACCESS_TOKEN`.

- Vérifications automatiques GitHub (`.github/workflows/verifications.yml`) à chaque pull request : zones, lint, types, tests (avec PostgreSQL), compilation, affichage (téléphone, iPad, ordinateur). Ne pas fusionner si une croix rouge apparaît.

## Repères techniques

- Next.js 16 : lire `AGENTS.md` et la doc dans `node_modules/next/dist/docs/` avant d'écrire du code (ex. `middleware` s'appelle désormais `proxy`, fichier `src/proxy.ts`).
- Connexions Supabase : `src/lib/supabase/client.ts` (navigateur) et `server.ts` (serveur).
- Sécurité de la base (revue du 24/11) : le contenu partagé (messages, questions, agenda, canaux, ressources, thèmes, partenaires, commentaires) exige un accès en cours, `acces_actif()` (même règle que `aAcces`) ; l'ancienneté `semaine_anciennete()` s'arrête à la fin de l'accès ; un ancien membre garde ses propres données. Le programme (`programme`, `blocs_seance`) n'est lisible que par le serveur (`createAdminClient` dans `src/lib/programme-serveur.ts`, après `exigerRole` : semaine affichée, séances du niveau et du profil du membre seulement) ; les membres ne lisent que `seances(id, sport, titre, duree_minutes)`. Preuves : `tests/securite-acces-actif.test.ts`, `tests/programme-serveur.test.ts`, `tests/securite-coach.test.ts` (l'encadrement ne modifie rien), `tests/securite-toutes-tables.test.ts` (**toute nouvelle table doit y être ajoutée**). Dans les tests, `base.abonnerTous()` donne un abonnement en cours aux membres de test.
- Toute modification de la base passe par un nouveau fichier dans `supabase/migrations/`, avec la sécurité par ligne activée et testée dans `tests/rls.test.ts` (base de test commune : `tests/aide/base-de-test.ts`). Toute nouvelle table de données personnelles doit être ajoutée à la preuve `tests/securite-tests-zones.test.ts` (lecture, modification, suppression, écriture au nom d'un autre). Appliquer avec `npm run migrations -- appliquer` (jamais à la main), puis vérifier avec `npm run migrations -- etat`. Attention : sur ce projet Supabase, une nouvelle table ne donne **aucun droit** par défaut, ni aux membres (`authenticated`) ni au serveur (`service_role`) : chaque migration accorde explicitement les droits nécessaires (la base de test `tests/supabase-shim.sql` reproduit ce comportement).
- Dates : utiliser `src/lib/dates.ts` (fuseau Europe/Paris), dont `dateDuJourParis()` pour les colonnes `date`.
- Tests de départ : mesures, pas et limites dans `src/lib/tests-depart.ts` ; écran `/tests` ; un test par membre et par jour (upsert). Les 4 mesures de la maquette sont obligatoires ; la puissance max sur 5 min à vélo (`tests.pma_5min`) est facultative (`facultative`, case « J'ai fait ce test », cochée d'avance si elle figurait au dernier test : `facultativesFaites`).
- Historique des tests : `historiqueSport(sport, membreId?)` dans `src/lib/historique-serveur.ts` (course, velo, natation, cardio), classé de la plus ancienne à la plus récente ; mise en forme testable dans `src/lib/historique.ts`.
- Zones : pourcentages dans `config/zones.json` (modifiable par Martin, validé avant chaque compilation par `npm run verifier-config`, logique dans `src/lib/config-zones.ts`), calculs dans `src/lib/zones.ts`, écran `/zones?sport=course|velo|natation|cardio` (onglet Cardio : zones en bpm d'après la FC seuil, `bornesDuClub`). Ne jamais écrire ces pourcentages en dur dans le code.
- Zones personnalisées : table `zones` (une ligne par membre et par sport, 6 bornes vérifiées par `bornes_valides`), règles dans `src/lib/zones-perso.ts`. Pas de ligne = valeurs du Club ; « Revenir aux valeurs du Club » supprime la ligne. Les zones cardio sont personnalisables (sport `cardio`) et s'appliquent aussi à la ligne FC sous la course, le vélo et les séances (`bornesFcPerso`).
- Niveau et profil : choisis par le membre (jamais de valeur par défaut), enregistrés dès qu'il touche une option (`ChoixNiveauProfil`, action `enregistrerChoix`), sous « Mes zones » et sur `/profil`. Le Profil mène aussi à Mes records (`/records`) et Mes progrès (`/progres`). Textes dans `config/profils.json` (validé par `npm run verifier-config`, logique dans `src/lib/config-profils.ts`). Profil suggéré (jamais coché à la place du membre) : FTP ÷ puissance max sur 5 min, seuils `suggestion` dans `config/profils.json` (provisoires : extensif à partir de 85 %, intensif sous 80 %, équilibré entre les deux), règle `profilSuggere` dans `src/lib/profil-suggere.ts`, texte et pastille « Suggéré » dans `ChoixNiveauProfil`.
- Ma saison (`/saison`) : objectifs du membre dans la table `objectifs` (bloc S, M, L, XL, `date_objectif` et `nom` facultatif, 60 caractères au plus : `lireNomCourse`, titre affiché `titreObjectif` = le nom, sinon « Triathlon M »). Durées des blocs dans `config/blocs.json` (validé par `npm run verifier-config`, logique dans `src/lib/config-blocs.ts`) ; S et XL sont provisoires. Règles testables dans `src/lib/saison.ts` (début du bloc = course − durée, statut, démarrage en cours de route, chevauchement : la course la plus proche mène, décompte « J-xx » / « Jour J », phase « Fil rouge » ou « Bloc M, semaine 3/12 »), lecture `lireObjectifs` dans `src/lib/saison-serveur.ts`, actions dans `src/app/(membre)/saison/actions.ts`. Le décompte (`CarteDecompte`) est aussi en haut de Ma semaine ; l'accueil affiche la phase (`phaseCourte`), la carte « Bloc en cours » / « Fil rouge » (`carteAccueil`), et dans l'ordre de la maquette les cartes « Aujourd'hui » (séance du jour, cochée si faite, « + 1 autre séance », sinon repos / semaine à venir / niveau à choisir : `carteAujourdhui`), « FAQ en visio » (`prochaineFaq`, questions non traitées : `texteQuestionsFaq`, « Poser une question ») et « Nouveau cette semaine » (contenu débloqué cette semaine-là, carte masquée sinon : `nouveauCetteSemaine`) ; règles dans `src/lib/accueil.ts`. Ma semaine : jours et titre dans `src/lib/semaine.ts`, bande des 7 jours `BandeJours`. Navigation entre semaines (`/semaine?du=AAAA-MM-JJ`, flèches ‹ ›) : de la semaine d'inscription (`Utilisateur.dateInscription`) à la semaine du dernier jour payé ou offert (`dernierJourPaye` ; l'équipe du Club voit 4 semaines à l'avance), règles `bornesSemaines`, `semaineDemandee`, `semainesVoisines` ; la phase et le programme sont ceux de la semaine affichée (son lundi), le décompte reste celui d'aujourd'hui. Calendrier réutilisable : `CalendrierMois` (`@/components/ui`).
